# Project Taskr Agent API

Use Project Taskr as the durable system of record for agent work. Do not rely on chat history or local markdown alone.

## Required References

Read before acting:

- [workflow.md](references/workflow.md): mandatory start-to-finish operating procedure and role rules.
- [api.md](references/api.md): endpoint contracts, scopes, event taxonomy, environment variables, and commands.

## Select The Flow

### Repository or coding work without an invitation code

Use the durable agent-session lifecycle:

1. Confirm branch and product boundary.
2. Ensure an active session before substantial work (`session:ensure` resumes or creates; it never opens a duplicate).
3. Record every prompt as a prompt-task (`session:prompt`) before the first mutation — even tiny prompts — and log each user-visible answer turn as `agent_message` (`session:message`).
4. Record plan, meaningful progress, decisions, errors, file changes, and tests.
5. Propose unfinished work as follow-ups; do not silently discard it.
6. Request approval/testing when human validation is required.
7. Verify, commit, and push according to the user request and repository rules.
8. Attach the final Git ref after the final commit exists.
9. Finish the session with an accurate status and verify it by reading it back.

Use the deterministic npm commands from `backend/package.json`; do not hand-roll secret handling.

### Work assigned through a Project Taskr work-session invitation

Use the connection/task lifecycle:

1. Authenticate, claim the provided `TASKR_SESSION_CODE`, and retain the connection ID.
2. Heartbeat while active and poll commands over HTTP.
3. Start only tasks delivered by a command with a `taskId`.
4. Record task events/artifacts/suggestions/test requests during execution.
5. Submit the task and acknowledge the command lease.
6. Never perform final acceptance. The prompt owner or reviewer accepts or reopens work.

WebSocket notifications are wake-up signals only; HTTP is authoritative.

## Non-Negotiable Rules

- Never print, commit, log, upload, or embed the agent key or JWT.
- Read the key through `backend/scripts/lib/agent-credentials.js`. On macOS it uses Keychain service `project-taskr-agent-key`; elsewhere use `TASKR_AGENT_KEY` through secure runtime injection.
- Never store secrets in session content, event metadata, artifacts, Git refs, errors, or memory. Redact before sending.
- Keep Project Taskr on `project-taskr`; do not mix Taskr Basic changes from `main`.
- Record user-visible plans and summaries, not hidden reasoning or chain-of-thought.
- Agents may submit, block, request changes/testing, or propose work. Only the prompt owner/reviewer can finally accept user-owned work.
- Do not finish a successful coding session before tests, final Git ref, push verification when applicable, and API read-back verification.
- On failure or interruption, record the blocker and finish with `failed` or `cancelled`; never leave an active session orphaned when cleanup is possible.

## Minimum Session Record

Every substantial session must contain:

- `session_started` generated by the API.
- A prompt-task (`user_prompt`) for every state-changing prompt, however small.
- `agent_plan` before implementation.
- `agent_message` for each user-visible answer turn, linked to its task.
- Progress events for meaningful milestones or decisions.
- `file_change` or Git metadata describing changed files.
- `test_result` for verification commands and outcomes.
- Follow-up records for known unfinished work.
- Approval/test request when human validation is required.
- A commit/push/PR/deployment Git ref when one exists.
- Final summary and `session_finished` with truthful status.

Small read-only questions may skip session creation only when no repository, API, project state, or external system is changed.
